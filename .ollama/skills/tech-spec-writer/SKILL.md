# Написание технического задания (ТЗ) по международным стандартам

Пишет техническое задание, структура и качество требований которого соответствуют
международным стандартам разработки требований: ISO/IEC/IEEE 29148:2018 (Requirements
engineering), IEEE 830-1998 (Software Requirements Specifications), ISO/IEC 25010
(SQuaRE — модель качества), ISO/IEC/IEEE 12207 (жизненный цикл). Подробное соответствие
разделов документа пунктам стандартов — в `references/standards.md`. Готовый скелет
документа — в `assets/template.md`.

## Рабочий процесс

1. **Сбор исходных данных.** Прежде чем писать ТЗ, задай вопросы (или используй уже
   предоставленный контекст), пока не закрыты минимум эти пункты:
   - Название и цель проекта, какую проблему решает, для кого (заказчик/пользователи).
   - Тип системы (веб/мобильное/десктоп/API/встроенная и т.д.), окружение и платформы.
   - Границы: что входит в объём (in scope) и что явно не входит (out of scope).
   - Заинтересованные стороны (stakeholders) и их роли.
   - Технические ограничения: стек, интеграции, существующие системы, регуляторные
     требования (например, GDPR, PCI DSS — если применимо).
   - Приоритеты нефункциональных требований (производительность, безопасность,
     надёжность, доступность, масштабируемость, удобство использования).
   - Сроки, бюджет, критерии приёмки, если известны.
   Не выдумывай факты о проекте. Любой неизвестный пункт помечай `[TBD]` и выноси в
   раздел «Открытые вопросы» в конце документа — не блокируй написание черновика.

2. **Скопируй `assets/template.md`** как основу и заполни каждый раздел по данным
   из шага 1. Не удаляй разделы стандарта, даже если по ним пока мало информации —
   оставляй `[TBD]` с уточняющим вопросом.

3. **Сформулируй требования по чек-листу качества** (полный список — в
   `references/standards.md`, раздел «Характеристики требования»). Каждое требование:
   - имеет уникальный ID (`FR-001`, `NFR-001`, `IR-001`, `DR-001` …);
   - атомарно (одно требование — одно утверждение, без «и»/«или», объединяющих
     разные требования);
   - однозначно и проверяемо (есть измеримый критерий приёмки и метод верификации:
     инспекция, демонстрация, тест, анализ);
   - имеет приоритет (MoSCoW: Must/Should/Could/Won't, либо Critical/High/Medium/Low);
   - трассируется к источнику (стейкхолдер, бизнес-цель, регуляторное требование).

4. **Классифицируй нефункциональные требования по ISO/IEC 25010**: функциональная
   пригодность, эффективность производительности, совместимость, удобство
   использования, надёжность, защищённость (security), сопровождаемость,
   переносимость (portability). Не сваливай всё в один нерасчленённый список.

5. **Построй матрицу трассируемости требований** (Requirements Traceability Matrix):
   ID требования → источник/потребность стейкхолдера → критерий приёмки → метод
   верификации. Это обязательный раздел по ISO/IEC/IEEE 29148.

6. **Собери единый глоссарий** терминов, сокращений и определений — используемых
   терминов должно быть достаточно, чтобы читатель без контекста понял документ.

7. **Самопроверка перед выдачей результата** — пройдись по чек-листу:
   - Все обязательные разделы стандарта присутствуют (см. `references/standards.md`).
   - Ни одно требование не дублирует и не противоречит другому.
   - У каждого требования есть ID, приоритет и критерий приёмки.
   - Раздел «Открытые вопросы» перечисляет все `[TBD]`.
   - Язык документа — язык, на котором пишет пользователь (по умолчанию русский);
     нумерация и структура разделов при этом остаются совместимы с международным
     стандартом (не GOST, если явно не попросили иначе).

## Формат вывода

Итоговый документ — Markdown, готовый к копированию в файл или дальнейшей конвертации
(например, в DOCX/PDF отдельным инструментом, если пользователь попросит). Не сокращай
обязательные разделы стандарта ради краткости ответа.

## Ресурсы

- `references/standards.md` — какой раздел ТЗ соответствует какому стандарту и пункту,
  полный чек-лист характеристик требования и обзор ISO/IEC 25010.
- `assets/template.md` — готовый скелет технического задания для заполнения.
