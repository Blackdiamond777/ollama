# Соответствие разделов ТЗ международным стандартам

Справочный материал для скилла `tech-spec-writer`. Загружай при необходимости
уточнить, к какому стандарту и пункту относится тот или иной раздел ТЗ, или чтобы
свериться с полным чек-листом качества требований.

## Используемые стандарты

| Стандарт | Название | Роль в этом скилле |
|---|---|---|
| ISO/IEC/IEEE 29148:2018 | Systems and software engineering — Life cycle processes — Requirements engineering | Основной каркас: процесс сбора требований, структура SRS, характеристики требований. Заменяет собой IEEE 830-1998 и IEEE 1233-1998, но их терминология всё ещё широко используется. |
| IEEE 830-1998 | Recommended Practice for Software Requirements Specifications | Классическая структура SRS-документа (разделы 1–3 ниже) и 8 признаков «хорошего» SRS. |
| ISO/IEC 25010:2011 (SQuaRE) | Systems and software Quality Requirements and Evaluation — quality model | Классификация нефункциональных требований по 8 характеристикам качества. |
| ISO/IEC/IEEE 12207:2017 | Software life cycle processes | Место ТЗ в жизненном цикле проекта (для раздела о процессе приёмки/сопровождения). |
| ISO/IEC/IEEE 42010:2011 | Systems and software engineering — Architecture description | Используется только для сложных систем: описание архитектурных точек зрения (viewpoints) как приложение к ТЗ. |

Если пользователь явно просит документ по ГОСТ (например, ГОСТ 34.602-2020 «Техническое
задание на автоматизированную систему») — это отдельный, не международный стандарт;
используй его вместо приведённого ниже только по прямой просьбе, не смешивая структуры
без предупреждения пользователя.

## Структура документа и её происхождение

1. **Введение** (IEEE 830 §1 / ISO 29148 «SRS content»)
   - Назначение документа (purpose)
   - Область действия (scope): что за система, что делает и не делает
   - Определения, акронимы, сокращения
   - Ссылки на другие документы
   - Обзор остальной части документа

2. **Общее описание** (IEEE 830 §2)
   - Взгляд на продукт (product perspective): встраивается ли в существующую систему
   - Функции продукта (product functions) — краткий обзор верхнего уровня
   - Классы/характеристики пользователей (user classes and characteristics)
   - Среда эксплуатации (operating environment)
   - Ограничения проектирования и реализации (design and implementation constraints)
   - Допущения и зависимости (assumptions and dependencies)

3. **Конкретные требования** (IEEE 830 §3, детализировано по ISO 29148)
   - 3.1 Функциональные требования (functional requirements) — сгруппированы по
     фиче/сценарию использования (use case / user story), каждое с уникальным ID
   - 3.2 Требования к внешним интерфейсам (external interface requirements):
     пользовательские интерфейсы, аппаратные интерфейсы, программные интерфейсы,
     интерфейсы связи (communication interfaces / API)
   - 3.3 Требования к производительности (performance requirements) — конкретные,
     измеримые (например, «95-й перцентиль времени ответа ≤ 300 мс при 1000 RPS»)
   - 3.4 Требования к данным (data requirements) — модель данных, хранение, миграция,
     сроки хранения
   - 3.5 Атрибуты качества системы / нефункциональные требования — см. классификацию
     по ISO/IEC 25010 ниже
   - 3.6 Требования к безопасности и защите информации
   - 3.7 Прочие требования (юридические, регуляторные, требования к документации)

4. **Критерии приёмки и верификации** — для каждого требования: метод верификации
   (inspection / demonstration / test / analysis — по ISO 29148) и измеримый критерий
   готовности.

5. **Матрица трассируемости требований** (Requirements Traceability Matrix) —
   обязательна по ISO/IEC/IEEE 29148: связывает требование с источником (бизнес-цель,
   стейкхолдер, регуляторное требование) и со способом его проверки.

6. **Глоссарий**

7. **Приложения** — диаграммы, макеты, реестр рисков, архитектурные точки зрения
   (ISO/IEC/IEEE 42010) для сложных систем, открытые вопросы.

## Характеристики отдельного требования

По ISO/IEC/IEEE 29148 и IEEE 830 хорошее требование должно быть:

- **Необходимым (Necessary)** — его отсутствие создаёт недостаток, который нужно устранить.
- **Однозначным (Unambiguous)** — читается одним и только одним способом.
- **Полным (Complete)** — самодостаточно, без «TBD» в финальной версии (в черновике —
  допустимо, но должно быть закрыто до подписания).
- **Атомарным / единичным (Singular)** — одно требование = одно утверждение.
- **Реализуемым (Feasible)** — достижимо в рамках бюджета, сроков, технологий.
- **Проверяемым (Verifiable)** — есть конечный, измеримый способ подтвердить выполнение.
- **Корректным (Correct)** — точно отражает реальную потребность.
- **Трассируемым (Traceable)** — имеет уникальный ID и связь с источником.
- **Ранжированным по важности/стабильности** — приоритет указан явно (MoSCoW или
  Critical/High/Medium/Low).

## Характеристики набора требований в целом

- **Полнота (Complete)** — все нужные требования присутствуют.
- **Непротиворечивость (Consistent)** — требования не конфликтуют между собой.
- **Ограниченность (Bounded)** — есть чёткие границы scope, включая явный список
  «вне рамок проекта» (out of scope).
- **Экономическая осуществимость (Affordable)** — реализуемо в рамках заявленного
  бюджета/срока (или явно помечено как риск, если бюджет неизвестен).

Восемь признаков «хорошего» SRS по IEEE 830: корректность, однозначность, полнота,
непротиворечивость, ранжированность по важности/стабильности, проверяемость,
модифицируемость, трассируемость.

## Классификация нефункциональных требований по ISO/IEC 25010 (SQuaRE)

1. **Functional suitability** (функциональная пригодность) — полнота, корректность,
   уместность функций.
2. **Performance efficiency** (эффективность производительности) — время отклика,
   использование ресурсов, ёмкость (capacity).
3. **Compatibility** (совместимость) — сосуществование с другими системами,
   интероперабельность.
4. **Usability** (удобство использования) — понятность, обучаемость, доступность
   (accessibility), защита от ошибок пользователя.
5. **Reliability** (надёжность) — устойчивость к сбоям (fault tolerance),
   восстанавливаемость (recoverability), доступность (availability), зрелость
   (maturity).
6. **Security** (защищённость) — конфиденциальность, целостность,
   неотказуемость (non-repudiation), подотчётность (accountability), аутентичность.
7. **Maintainability** (сопровождаемость) — модульность, повторное использование,
   анализируемость, модифицируемость, тестируемость.
8. **Portability** (переносимость) — адаптируемость, простота установки,
   заменяемость.

Каждое нефункциональное требование в разделе 3.5 ТЗ должно быть отнесено к одной из
этих восьми категорий и, где возможно, снабжено измеримым порогом (SLA/SLO), а не
общей формулировкой вроде «система должна быть быстрой».

## Методы верификации (ISO/IEC/IEEE 29148)

- **Inspection** — проверка документации/кода без выполнения (ревью, чек-лист).
- **Analysis** — расчёт, моделирование, анализ (например, нагрузочная модель).
- **Demonstration** — показ работающей функции в реалистичных условиях без
  инструментального контроля.
- **Test** — выполнение с контролируемыми входами и измерением результата
  (автотесты, нагрузочное тестирование, пентест).

Указывай метод верификации для каждого требования — это то, что превращает ТЗ из
списка пожеланий в проверяемый контракт.
